## Key Design Decisions

1. **No mobile drag-and-drop** — Mobile uses tap-to-select, then tap-tier to place (for vote tierlists). Regular tierlists use @dnd-kit which has pointer sensor support.
2. **Client-side image compression** — Reduces upload size before hitting Supabase Storage. WebP format for smaller files.
3. **Anonymous voting** — localStorage UUID enables voting without login, with one-vote-per-image constraint.
4. **Service-role client** — Used server-side for admin operations and cross-user queries (bypasses RLS).
5. **html2canvas for export** — Screenshots the tier rows div directly, no server-side rendering needed.
6. **Slug generation** — Auto-generated from title with random suffix for uniqueness.

### Critical Gotchas

1. **Never add columns to the admin page's initial `select()` query that don't exist in the DB yet** — Supabase returns an error (not empty results) when selecting a non-existent column, which causes the entire query to fail silently and show 0 tierlists. The admin page (`app/admin/page.tsx`) only selects: `id, title, category, cover_image_url, created_at, created_by, slug`. Extra data (tiers, images, etc.) is fetched lazily when opening the edit form.
2. **Supabase Storage structure** — All images are in the `tierlist-images` bucket as flat files with UUID filenames (plus subfolders: `cover-crops/`, `profile-saves/`, `vote-covers/`). There is no per-tierlist folder organization. Image URLs are stored in DB tables (`tierlist_images`, `vote_tierlist_images`).
3. **Image uploads** — Images are compressed client-side to WebP (1200px max, 75% quality) before upload. File names are random UUIDs. Uploaded via Supabase Storage JS client.
4. **Admin panel component (`AdminPanel.tsx`)** — ~2650 lines, contains both regular tierlist and vote tierlist management. Uses `@dnd-kit` for image reordering. Both regular tierlists and vote tierlists use a centralized batch-save pattern (`EditState` for regular, `VoteEditState` for vote) — no changes persist to DB until the user clicks Save Changes.
5. **`NEXT_PUBLIC_SUPABASE_URL` must ALWAYS point to the Supabase project URL** (e.g. `https://cagkgfketucousksgtbk.supabase.co`), NEVER the app/Vercel URL. Setting it to the app URL causes `MIDDLEWARE_INVOCATION_FAILED` (500 on every page).
6. **Supabase OAuth redirect URLs** — Must include `https://knowitball.co.uk/**` (production wildcard) and optionally the Vercel preview wildcard. The **Site URL** in Supabase Auth config must also be `https://knowitball.co.uk`.

## ALWAYS PLAYTEST STAR CAREER CHANGES — you can now actually see the game

> This supersedes every earlier note in this file claiming `/star-dev` can't be
> reached without Google sign-in. **It can.** Those notes are why round after
> round of gameplay work shipped saying "none of this has been seen live", and
> why several real bugs (keeper frozen mid-dive, the face outline tracing a
> rectangle, Touch Mode catching instantly, every team sheet full of
> silhouettes) each survived multiple type-clean, test-green rounds.

`/star-dev` has **no server auth gate** — `middleware.ts` only guards
`/tierlist` and `/create`. `lib/star/devMode.ts` re-enables the local-only
`ANON_SCOPE` career in development, so the game is fully playable signed-out in
a sandbox or CI. A production build inlines `NODE_ENV` to `"production"`, so
this cannot reach the live site.

**After ANY change to `lib/star/**`, `components/star/**`, `app/star-dev/**`,
or the star/draft data routes, invoke the `star-playtest` subagent** (see
`.claude/agents/star-playtest.md`) and act on what it reports. A type-check and
a green suite are necessary, not sufficient — neither can see a frozen figure,
a mis-cropped face, or a button that never appears.

Harness: `scripts/star-sandbox/` (`drive.mjs`, `play.mjs`, `match.mjs`,
`explore.mjs`) — read its README first.

**Env:** `.env.local` needs only `NEXT_PUBLIC_SUPABASE_URL` and
`NEXT_PUBLIC_SUPABASE_ANON_KEY`. The anon key is **not a secret** (it ships in
the browser bundle of every live page) and is sufficient for real player data,
because every table the career reads is public-read by RLS: `sofifa_players`,
`club_logos`, `league_logos`, `star_lineups`. `SUPABASE_SERVICE_ROLE_KEY` is
NOT needed — `lib/supabase/publicRead.ts` falls back to the anon key for the
read-only data routes, and production is unchanged whenever the service key is
present.

**Without valid Supabase env**, every club shows "NO SQUAD YET" and falls back
to invented players. Physics/layout work is still testable; anything involving
real players is not.

**The green pre-match button is "Team sheets →", not "Play Match".** It reads
"Play Match ⚽" only when your XI is under 9 players (`teamsReady`, page.tsx) —
otherwise it routes via VersusScreen, which has its own KICK OFF. An earlier
version of this note claimed the button disappeared entirely without squad
data; that was wrong, and came from a script searching for the wrong text
rather than looking at the screen. Match on all of it.

**In-match, the ball is NOT centre-bottom.** That's only true of the trial
penalty. A real scenario places it anywhere in the framed view, so a driver
that drags from a fixed point will miss and silently produce no contact
screen. Find the ball before aiming.

## How to talk to this team (standing, not per-session)

Neither Harry nor Mikey writes code. Stated directly: *"we AREN'T coders -
english only."* Everything below is a standing instruction, confirmed more
than once.

**Answer shape — key point, key number, key change.** Reported directly:
*"there's sometimes too much fluff in how you speak… I'm having to skim
through too much yap."* No preamble, no restating the request, no praise for
the idea, no tour of the code. Name things the way they appear on screen; put
the file in brackets after, once, only if someone needs to find it.

**Every claim carries a number, or admits it has none.** "Scoring is hard" is
not a finding. "A clean one-on-one converts at 0.0% over 250 simulated
matches" is. Always give the before alongside the after.

**Say whether you saw it, measured it, or reasoned it.** This project's real
bugs have all lived in "reasoned it" — a keeper who reacted and didn't, a
price that was three weeks and was three weeks *per match*. "I read the code
and worked it out, I haven't seen it on a screen" is a fine thing to say and
tells them whether to go and look.

**Show, don't describe, anything with a size or a shape in it.** Goal width,
figure proportions, prices, framing, difficulty. Render the options at real
phone size and let them point. Use the `show-options` agent.

**Play it before claiming it works.** A type-check and a green suite cannot
see a frozen figure or a box sitting on the ball. Use `star-playtest`.

**Ask about the one ambiguous word; build the rest.** Never block a whole
message on one unclear clause. Build what is clear, then ask one question with
its options so it can be answered in a word from a phone.

**Do not agree to be agreeable.** Caught directly: *"a lot of times you're
just agreeing with us… I want to know for sure if that is a good idea."*
Before agreeing with a design call, go and find what argues against it. If
nothing does, say what you checked.

**The change list goes out before the push, every time** — written so it
survives being forwarded to someone who wasn't in the conversation. Shared
files (`app/star-dev/page.tsx`, `lib/star/types.ts`, tailwind config) get
named explicitly.

**Two hard rules on the match engine, from Mikey:** only ever ADD to gameplay,
never change it; and never modify `lib/star/canvasEngine.ts`.

**21 September 2026 — Headers, volleys, and first-time grounded finishes: the first piece of a "mega prompt," and the first receiver mechanic gated on WHEN the ball reaches him, not just how good he is.**

- **The ask, in full, one message** — the start of a stated "mega prompt... test things out and feel them in the game": a real header mechanic for crosses ("cross it onto my teammates heads and they head it towards goal — ideally towards top corners, away from goalie, decent power, first time obvs"), named directly against the exact frustration it fixes ("taking corner scenarios and doing PERFECT crosses into the box right onto a teammates head just to watch him take a touch and not only let the goalie have time to react but also SHOOT RIGHT INTO THE GOALIES HANDS"); a second, explicit decision-gating instruction ("levels of decision making affected by the player's attacking ability and quality, similar to how the teammates chipping the goalie works now... again; only when 'crossed' to"); first-time GROUNDED finishes made likelier for a better finisher ("Haaland should be noticeably doing incredible first time curved top corner 'bangers' much more... than the average player"); and a third, distinct volley finish ("far more potential for power, as well as far more potential to miss the target... the better the finisher the less of an issue this is").
- **The root cause, found before any code was written**: `launchReceiverShot` (canvasEngine.ts) — the one function that already governs every AI-teammate reception, including the existing chip-the-exposed-keeper decision this was asked to mirror — has never once read the ball's HEIGHT. `RECEIVER_CONTROL_T` (0.45s) holds every clean reception at his feet, unconditionally, before an ordinary grounded shot; a genuinely elevated cross reaching his head was snapped to `z = 0.08` the instant it arrived (stepBallRaw's own reception block), making a header physically impossible to model at all — not a tuning gap, a missing signal.
- **Measured before designing the gate, not assumed**: reception (`swept < PASS_CONTROL_R`) is pure XY distance, no height check at all — so a first pass at "if it's still off the ground, it's a header" was tested directly against real `buildScenario` output and found far too broad. A `cutback` — RECEIVER_CONTROL's own words, "on the floor, into his stride" — still hasn't finished descending by the time it geometrically reaches the runner a measured **~70% of the time** (500-trial sample), the same order of magnitude as `through_ball`. Height alone would have read most of those as a header, exactly what "again; only when 'crossed' to" was warning against. Fixed by gating on `CROSS_DELIVERY_KINDS` (corner, byline_cross — the one signal this engine already has for "this delivery is genuinely a cross," the same one `CROSS_VZ_CAP` already keys off) as well as height. Honest scope note, not silently under-delivered: a lofted header from open play (a deliberately chipped through-ball or midfield pass) is a real, reasonable future extension this does NOT cover yet — height alone can't tell "deliberately lofted" apart from "just hasn't landed" for a kind never built as a cross, and getting that wrong is worse than not having it.
- **The mechanism — `strikeModeForHeight(kind, z)`** (exported, pure): reads the real `ball.z` at the instant of reception (captured before the caller's own reset) against two bands — `HEADER_MIN_Z` (1.3m, a real jump-and-head contact height) up to `HEADER_MAX_REACH_Z` (2.6m, above which nobody could realistically reach it — falls back to ground rather than reading as a phantom volley, a real bug caught by the new test suite before shipping, see below) is a header; `VOLLEY_MIN_Z` (0.35m) up to the header floor is a volley; anything lower, or off a non-cross kind, is ground. **`firstTimeChance(mode, quality)`** (exported, pure) is the decision itself, deliberately shaped like `CHIP_KEEPER_Y`'s own quality-gated chance rather than a fresh mechanism: header's floor is high (0.5, climbing to 0.92) because a ball at head height was never really a "control it first" situation for a real footballer; volley's floor is lower (0.35→0.85, a genuinely harder technical call); ground's floor is **zero** below quality 0.35, climbing only to 0.55 at maximum — "first time finishes of normal shots... likelier as the finisher gets better," not a guarantee for anyone.
- **Header physics — a real strike, not a foot-strike that starts higher up.** Power comes off a slower, physical-strength-leaning formula (`10 + composite·0.11`, boosted by `receiver.who?.physical`, falling back to `overall`) rather than the ordinary Sh formula. Height is a genuine closed-form solve — given horizontal speed and flight time, `z(t) = arrivalZ + vz·t − ½gt²` rearranges directly for the `vz` that lands it at a real target height (`HEADER_TARGET_Z_MIN/MAX`, 1.5-2.15m, "top corners" as literally asked rather than the textbook-correct downward header) — widened by the SAME placement roll that already decides how close to the frame he's aiming in X, so a confident header is high and wide together, not two independent dice. No curl (a header has no side-of-the-boot contact to bend it) and no chip (a delicate lofted touch and a header are different actions). Measured directly: mean crossing height 1.4-1.5m, p75 up to 1.9m, comfortably under the bar; placed away from the keeper's actual position 70-96% of the time.
- **Volley physics — reuses the ordinary shot model with two real adjustments, not a parallel system**: `Sh` gets a randomised 1.0-1.55× power ceiling ("far more potential for power" — a raised ceiling, not just a higher average), and `sigmaDeg` gets `(1 − quality) × VOLLEY_MISS_PENALTY_DEG` added on top of the ordinary spread — real for an average finisher, close to nothing for an elite one, exactly the stated trade. Keeps full curl and remains chip-eligible (a dinked volley over an exposed keeper is a real technique); a header is not.
- **Two real bugs found by measuring, not by inspection, and fixed before shipping — both documented inline at the fix, this project's own established discipline:**
  1. `strikeModeForHeight`'s own height ceiling only excluded the HEADER band, so an impossibly high ball (>2.6m) fell straight through into "z ≥ VOLLEY_MIN_Z" and read as a volley — backwards from the doc's own stated intent. Caught by the new test file's own boundary sweep, not spotted by re-reading the code.
  2. A real, reproducible wall-defender regression: adding ground-mode first-time firing made an elite finisher (92 shooting) get BLOCKED more often than a no-identity receiver in a `one_on_one` chance — the opposite of the existing, already-shipped curl-around-a-defender mechanic's whole point. Root-caused by measuring, in stages: first ruled out the just-added chip-eligibility interaction (a `rushed` flag now excludes chip from a ground-mode first-time strike on its own separate reasoning — a rushed "banger" and a delicate lob are different decisions — but this alone didn't fix the reversal); then found the real mechanism — firing immediately denies a still-recovering real defender the same half-second the ordinary 0.45s hold would have given him to run clear, so a first-time shot can genuinely catch a MORE dangerous defender than a held one, not just a less-ready keeper. Fixed with a `threatened` check at the reception site, reusing `nearThreat`'s own established goal-side catchment shape (not a cruder omnidirectional radius, which measurably did NOT fix it) — a first-time grounded shot is now only attempted when the space is genuinely there. (viewport - w) / 2 : …`) — a picture can have one dimension still covering (edge-clamped as always) while the other has zoomed out past covering (centred), which is exactly the shape a portrait image zoomed out to fit-height needs. `sourceRect` then legitimately samples a rectangle bigger than and centred outside the source image's own bounds — relied on the standard, spec-mandated canvas `drawImage` behavior (out-of-bounds source clips, with the destination rectangle shrinking in the same proportion) to render that correctly as "image centred and slightly smaller, backing colour showing as margin," rather than reimplementing letterboxing by hand.
