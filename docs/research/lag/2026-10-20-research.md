### Pass/fail bar for "zero lag" (proposed, tune after the baseline)

- **Menus:** new screen shown ≤ 300 ms warm. Back to Home ≤ 300 ms.
- **Soak:** minute 15's p95 within 10% of minute 1's.

## 3. Part B: best practice, with sources

### B1. Frame pacing on phones
- **Budget.** 60 Hz = 16.7 ms. 90 Hz = 11.1 ms. 120 Hz = 8.3 ms. iPhone Low Power Mode = 33.3 ms. [arithmetic]
- **Your own work is about 10 ms at 60 Hz**, because the browser needs about 6 ms. RAIL: "Produce each frame in an animation in 10 ms or less." Respond to input in 100 ms. Process input events in 50 ms. Idle work in chunks of 50 ms or less. [sourced: [web.dev RAIL](https://web.dev/articles/rail)]
- **Low Power Mode caps rAF at 30 fps on purpose.** WebKit engineer, 2020: "intentional", "a little bit rough but it is okay". WebKit also says rAF is "not guaranteed" at 60 when a frame is complex, the device is busy or hot, or memory is short. [sourced: [WebKit bug 215745](https://bugs.webkit.org/show_bug.cgi?id=215745)]
- **Safari limits page rendering to about 60 fps by default** through a feature flag, "Prefer Page Rendering Updates near 60fps". Switching it off lets pages run up to 120 fps on ProMotion iPhones. This comes from secondary blogs, not Apple. [sourced, weak: [iphone-ticker](https://www.iphone-ticker.de/promotion-im-web-freischalten-so-nutzt-safari-die-volle-bildrate-271471/), [iGeeksBlog](https://www.igeeksblog.com/this-hidden-safari-setting-unlocks-120hz-scrolling/)] Unknown for the Home Screen app. Test it.
- **No browser API gives the refresh rate.** Adaptive 75/90/120 Hz screens change it while you play. Estimate it from the median rAF gap. [sourced, weak: [PlayCanvas forum](https://forum.playcanvas.com/t/fps-rate-jumps-on-gameplay/42320), [Kirupa](https://www.kirupa.com/animations/ensuring_consistent_animation_speeds.htm)]
- **Heat.** Long sessions raise temperature, then frame rate falls. Netmarble's fix on Android: Adaptive Performance, resolution scaling and a dynamic frame rate. Samsung (Call of Duty Mobile): lower the target frame rate when temperature climbs fast. A higher rate always costs more power and heat. [sourced: [Android](https://developer.android.com/stories/games/netmarble-got-adpf), [Samsung](https://developer.samsung.com/galaxy-gamedev/gamedev-blog/cod.html)] One study saw a game fall from 35 to 23 fps (about −34%) when the GPU throttled. [sourced: [ar5iv 1904.09814](https://ar5iv.org/html/1904.09814)] One Unity guide says profile 20-minute sessions, because the first minutes run before the phone heats up. [sourced, weak: [oceanviewgames](https://oceanviewgames.co.uk/blog/posts/managing-thermal-throttling-unity-mobile)] I found no Apple guidance. There is no web API for thermal state.
- **A fixed step beats a variable step for physics.** Forum advice: fixed 60 Hz with an accumulator and interpolated drawing. A large frame gap broke physics on Android Chrome. [sourced, weak: [Babylon forum](https://forum.babylonjs.com/t/havok-physics-behavior-is-different-on-android-chrome-106/41474)]

**For us.** (a) Decide the cap on 90/120 Hz (L7). (b) Teach the governor about Low Power Mode (L20): when idle rAF gaps sit at 33 ms, 33 ms is "on time". (c) Add a long soak to every test. (d) Ask the engine lane about L21.

### B2. React and Next.js
- **Keep the loop out of React state.** The 2D match already does (a code comment says so, and commits are 0–0.8 a second). [read]
- **Find the big modules first.** `@next/bundle-analyzer` (`ANALYZE=true next build`) draws each module's size. Start with the biggest. [sourced: [Next.js 14 docs](https://nextjs.org/docs/14/app/building-your-application/optimizing/bundle-analyzer)]
- **Every `"use client"` file goes to the browser.** `/star-dev` is one 272 KB client page. [sourced, weak: [webkul](https://webkul.com/blog/how-to-reduce-javascript-for-better-next-js-speed/); file size measured]
- **Big data: `JSON.parse` of a string beats a JS object literal on a cold load, 1.2× to 2.0×, on a 7.33 MB array. Rule of thumb: 10 kB or more.** Best of all, do not ship it until needed. [sourced: [V8 benchmark](https://goo.gle/json-parse-bench), [erdem.pl](https://erdem.pl/2019/08/can-json-parse-be-performance-improvement)]
- **Yield inside long jobs.** A task over 50 ms is a long task. `scheduler.yield()` works in Chrome 129+, Edge 129+ and Firefox 142+, **not Safari**. Fall back to `setTimeout(0)`. After five nested `setTimeout` calls the browser adds 5 ms. `isInputPending()` is Chrome-only and no longer recommended. [sourced: [web.dev](https://web.dev/articles/optimize-long-tasks)] The repo's encoder already yields with `setTimeout(0)`.
- **INP "good" is 200 ms or less at the 75th percentile on mobile.** We want stricter. [sourced: [web.dev INP](https://web.dev/articles/inp)]

### B3. 2D canvas
- MDN's list: draw repeated things once to an offscreen canvas. Use whole-pixel coordinates. Do not scale inside `drawImage`. Layer canvases by how often they change. Use CSS for big static backgrounds. Scale with CSS transforms. `getContext("2d", { alpha: false })` when transparency is not needed. Scale for `devicePixelRatio`. Batch calls. Avoid state changes, `shadowBlur` and text. Use rAF, not `setInterval`. [sourced: [MDN](https://developer.mozilla.org/en-US/docs/Web/API/Canvas_API/Tutorial/Optimizing_canvas)]
- **Garbage collection.** Create nothing in the frame loop if you can. `map`, `filter`, spread and closures in hot paths all allocate. Pools help. Pause sizes are quoted as 5–30 ms or 100 ms, with no measured source. A steady sawtooth in the memory graph is the sign. [sourced, weak: [Construct blog](https://www.construct.net/en/blogs/construct-official-blog-1/write-low-garbage-real-time-761)]
- **`desynchronized: true`** skips compositing for low latency (Chrome 75+). One source says it is not available on Android or iOS, and I found no current table. [sourced, dated: [Chrome](https://developer.chrome.com/blog/desynchronized), [Thinktecture](https://www.thinktecture.com/en/?p=4858)] Do not plan on it.
- **OffscreenCanvas.** WebGL in a worker works on Safari/iOS 17+. iOS 16.4–16.7 has 2D only. [sourced: [caniuse](https://caniuse.com/offscreencanvas), [WebKit bug 263010](https://bugs.webkit.org/show_bug.cgi?id=263010)]
- **`backdrop-filter`.** The browser re-composites everything behind the glass each frame. Anecdotes only: animating blur drops phones to about 30 fps. Keep blur under about 20 px and 3–4 glass layers in view. [sourced, weak: [OpenReplay](https://blog.openreplay.com/creating-blurred-backgrounds-css-backdrop-filter/)]
- **`content-visibility: auto`** skips layout and paint for off-screen items. It needs `contain-intrinsic-size`. Safari 18+ per a secondary table. I found no verified speed-up figure. [sourced, weak: [DebugBear](https://www.debugbear.com/blog/content-visibility-api)]

**For us.** The 2D draw already avoids the usual traps (2.5). So the 66.7 ms flight frames are probably not drawing. The suspects are the hidden-match step, commentary, React, or GC. Profile first (item 4).

### B4. three.js and WebGL
- **Mobile budgets (one guide):** under 100 draw calls and under 100,000 vertices. Instance repeats: 1,000 trees as one `InstancedMesh` = 1 draw. [sourced: [Utsubo tips 30–31](https://www.utsubo.com/blog/threejs-best-practices-100-tips)] Our career 3D after pass 2: 80 draws and 512k triangles on the rig [measured]. Draws pass. Triangles are 5× that guide's vertex figure, so shadow-map triangles and skinned men are what to count.
- **Pixel ratio.** Cap at 2. A DPR-3 phone has 9× the pixels of a 1× screen. Half-resolution post can "roughly double" frame rate when fill-bound. Shadow maps 512–1024 on mobile. About 3 dynamic lights or fewer. A point-light shadow draws 6 faces. [sourced: Utsubo tips 53–57, 80] Our tiers already follow this (cap 1.5–2, 1024 on Medium).
- **Compressed textures.** KTX2 + Basis uses 4–8× less GPU memory than PNG/JPEG. A 2048² PNG is about 21 MiB of VRAM with mipmaps. A 4096² RGBA is 85 MiB. [sourced: Utsubo tips 22, 27, 37] We did this for 13 maps and the shop. Our ETC1S files were bigger downloads than WebP (2.0 vs 1.1 MB) [measured, handbook]. The win is memory, not bytes.
- **Meshopt decodes faster than Draco.** Draco's WASM decoder can cost more than it saves on small models. [sourced: Utsubo tips 21, 29] Three's `MeshoptDecoder` has `useWorkers(count)` [read in `node_modules/three/examples/jsm/libs/meshopt_decoder.module.js`]. We never call it.
- **Shader compile stalls.** Compile under the loading screen with `compileAsync`. WebGL can use `KHR_parallel_shader_compile`. [sourced: Utsubo tip 5] In r169, `isReady()` polls `COMPLETION_STATUS_KHR`, and the log reads in `onFirstUse` run only when `checkShaderErrors` is true. [measured: I read the r169 source] Status checks before a link finishes block and kill the parallel win. [sourced: [Khronos list, 2019](https://www.khronos.org/webgl/public-mailing-list/public_webgl/1904/msg00035.php)] **Caveat for item 6:** if `compileAsync` already finished a program, the later log reads are cheap. The 7.6 s gain was on a rig with no parallel compile.
- **Image decode.** three's glTF loader uses `ImageBitmapLoader` (decode off the main thread) except on Safari older than 17 and old Firefox. [measured: read r169 `GLTFLoader.js` ~2569–2596] The texture upload still runs on the main thread and can take tens of ms for a big map (one report: 70 ms for 1920×6000). KTX2 makes the upload smaller. [sourced, weak: [three forum](https://discourse.threejs.org/t/performance-ideas-loading-objects-in-workers-faster-texture-uploads-etc/25328), [WebGL fundamentals](https://webglfundamentals.org/webgl/lessons/webgl-qna-how-to-load-images-in-the-background-with-no-jank.html)]
- **Contexts.** Browsers evict the oldest WebGL context when a page has too many. The quoted limit is about 16 on desktop Chrome and Safari, fewer on mobile, with no primary source for iOS. [sourced: [WebKit layout test](https://webkit.googlesource.com/WebKit/+/master/LayoutTests/webgl/max-active-contexts-oldest-context-lost-expected.txt)] Reuse one renderer. Handle `webglcontextlost`. The shared layer does.
- **iPhone memory.** Heavy WebGL pages are killed under memory pressure and reload, which can loop to "A problem repeatedly occurred". The limit is not published and moves with other apps. There is no catchable error. [sourced: [WebKit bug 300782](https://bugs.webkit.org/show_bug.cgi?id=300782), [three forum](https://discourse.threejs.org/t/a-problem-repeatedly-occurred-in-safari-when-shadow-map-size-too-big/44542)]
- **WebGPU in 2026.** Safari 26 on iOS/iPadOS 26. Chrome 121+ on Android 12+ with Qualcomm or ARM GPUs. [sourced: [web.dev, Nov 2025](https://web.dev/blog/webgpu-supported-major-browsers)] three's WebGPU renderer is called production-ready from r171 [sourced, weak: Utsubo]. We are on r169 with patched shaders (toon, look H, baked light). Not a same-quality move.
- **Draw only when something changes.** `frameloop="demand"` saves battery. [sourced: Utsubo tip 64] Our scenes already do this for still shots (`stillFps` 20).

### B5. Loading
- **Code-split.** We have `lazyScreen`, and the first load is still 4.07 MB raw. [measured]
- **Preload vs run.** A dynamic `import()` fetches and runs. A `<link rel="prefetch">` or `fetch()` into the HTTP cache only fetches. [reasoned] Whether Next 14's app router honours `/* webpackPrefetch: true */` needs a quick test.
- **The HTTP cache is already strong.** `?v=hash` files are `max-age=31536000, immutable` [read `next.config.mjs`]. A service worker adds little. Safari deletes script-writable storage, service-worker caches included, after 7 days without use. Whether Home Screen apps are exempt is disputed. [sourced: [Search Engine Land](https://searchengineland.com/what-safaris-7-day-cap-on-script-writeable-storage-means-for-pwa-developers-332519), [WebKit bug 237350](https://bugs.webkit.org/show_bug.cgi?id=237350)] Skip it.
- **Live check, signed out, today.** Repeat requests for `/star/…` files return `cache-control: public, max-age=86400, stale-while-revalidate=604800` and `x-vercel-cache: HIT`. [measured by `curl`]
- **No `<link rel="preload">` or `fetchpriority` anywhere in the app** [grep: 0 hits]. Small gains only.

### B6. Input latency
- Respond to a tap within 100 ms. Handle events in 50 ms. [sourced: RAIL]
- Chrome aligns pointer events to frames (since Chrome 60). `getCoalescedEvents()` returns the full path between frames. `getPredictedEvents()` can draw ahead. [sourced: [Chrome blog](https://developer.chrome.com/blog/aligning-input-events)] Our aim drag could read coalesced events for a smoother arrow. Gain unknown.
- "Latencies longer than 50 ms can interfere with a user's hand-eye coordination" is the figure behind `desynchronized`. [sourced: Chrome blog] We use it as the drag-aim bar.
- `touch-action: none` is already on the match canvas (`CanvasMatch.tsx:9107`). [read]

### B7. How to measure
- **In the page.** `PerformanceObserver` with `long-animation-frame`: frames over 50 ms, with `blockingDuration`, `renderStart` and `scripts[]` (source URL, function, forced-layout time). Buffer holds 200. **Chrome and Edge 123+ only. Safari supports neither it nor `longtask`.** [sourced: [MDN](https://developer.mozilla.org/en-US/docs/Web/API/Performance_API/Long_animation_frame_timing), [W3C WD Apr 2026](https://www.w3.org/TR/long-animation-frames/), [Chrome docs](https://developer.chrome.com/docs/web-platform/long-animation-frames)] On iPhone we need our own: rAF gaps plus an event-loop heartbeat.
- **Chrome CPU throttle.** DevTools can calibrate "low-tier mobile" and "mid-tier mobile" presets for the machine (Chrome 134+). Mid-tier was 3.7× on the author's machine and will differ here. Throttling cannot slow the GPU. [sourced: [Chrome blog](https://developer.chrome.com/blog/devtools-grounded-real-world)] Lighthouse's default is a Moto G Power at 4×. Lighthouse and desktop runs miss thermal, OS background load and touch latency. [sourced: [Shopify guide](https://shopify.dev/docs/storefronts/themes/best-practices/performance/improve-mobile-page-load-speed)] The CDP command is `Emulation.setCPUThrottlingRate`. [sourced: [Focusreactive](https://focusreactive.com/testing-web-application-performance-with-playwright/)]
- **Safari on iPhone.** Web Inspector from a Mac. Timelines tab, **Rendering Frames** view (tall bar = slow frame, 16.667 ms budget), CPU timeline. `console.profile` scopes a recording. Debug features switch off during recording. [sourced: [WebKit blog](https://webkit.org/blog/3996/introducing-the-rendering-frames-timeline/), [WebKit Timelines](https://webkit.org/web-inspector/timelines-tab/), [DebugBear](https://www.debugbear.com/blog/safari-developer-tools)] A Mac is needed.
- **Chrome on Android.** USB debugging, `chrome://inspect#devices`, then Inspect. The page I fetched does not say the Performance panel records remotely, so that part is not from the source. [sourced: [Chrome docs](https://developer.chrome.com/docs/devtools/remote-debugging)]
- **Chrome traces** carry a `PipelineReporter` event per frame: presented or dropped, and why. [sourced, weak: [Perfetto commit](https://chromium.googlesource.com/external/github.com/google/perfetto/+/530ca4c2de23b9724c87008acf695d91a5b2bb0e)]

### 5.0 Device tiers (Harry, 20 Oct 2026)
*"judge lag on a high performance phone (iphone 16 +), mid performance iphone 13/14 and low performance (older android), same for pc"*

| Tier | Phone | Computer | Trace here (CPU slow-down) | Real-device pass |
|---|---|---|---|---|
| High | iPhone 16 or newer | gaming PC or new laptop with its own graphics card | none | needed (GPU, 120 Hz screens) |
| Mid | iPhone 13 / 14 | 3–5 year old laptop, built-in graphics (Iris Xe, M1 Air class) | Chrome "mid-tier mobile" preset | needed |
| Low | older Android (about 2019–21 mid-range, 3–4 GB) | old office laptop (UHD 620 class, 4–8 GB) | Chrome "low-tier mobile" preset, plus 4× | needed |

- Every screen is judged on all six. A fix counts only if it holds on all six and no tier gets worse.
- This machine has no graphics chip, so traces here judge the CPU side only. The GPU side, heat and refresh rate come from the in-game Perf recorder (Step 0) on a real device of each tier.
- Bars per tier: the 5.4 bars at the screen's own refresh rate (60 Hz; 120 Hz on a ProMotion iPhone; 144 Hz PC where present).
- Low tier in 3D (Harry, 20 Oct: "less frames is okay"): a steady 30 fps passes. Steady means p95 frame ≤ 1.25 × 33.3 ms and no frame over 100 ms. Same picture quality; 2D still holds 60.
- Simulated vs real (Harry asked if it could all be simulated). Simulated here: the processor side of every tier (Chrome's CPU slow-down presets), loading on a slow network, and the 3D work counted per frame (draws, triangles, texture memory) against each tier's budget. Not simulatable here: the graphics chip (this machine has none, so 3D runs in software, slower than any real phone and in a different way), heat, and 120 Hz screens. Those need a real device per tier: a team phone with the Perf recorder, or a paid cloud device service (real iPhones and Androids run remotely).

### 5.1 Three independent methods

**Method 1: static audit (no page run).**
- Catches: bytes, eager imports, loops, per-frame allocations, synchronous calls (`localStorage`, `toDataURL`, `getImageData`, big `JSON.parse`, shader logs), GL context count, texture memory, headers, the middleware matcher.
- Cannot catch: how long anything takes.

**Method 2: scripted traces.**
- Setup: Chromium, 390×844, DPR 3. Production build (`next build && next start`, offline-dev flag so a save plays). CPU slowed with Chrome's calibrated mid-tier and low-tier presets, plus the old 4×. Network "Fast 4G" 9 Mbit/150 ms. 5 runs each, drop the first, report the median and the spread.
- Catches: long tasks, frame gaps, React commits, shaders built after ready, JS per frame, draws, triangles, texture MB, load times, memory growth.
- Cannot catch: GPU time (software GPU), thermal, real touch latency, iOS Safari differences.

**Method 3: a different agent, new code, final build.**
- It writes its own driver from this spec, not the Method 2 scripts. It runs the same route list.
- Plus a **real-device pass** on each of the six tiers in 5.0, using the Perf recorder on a scripted 10-minute route. Add Web Inspector (Mac) or Chrome remote debugging if available.
- Catches: a bug in the harness, numbers that depend on one script, GPU, heat, memory kills, refresh rate.
- Cannot catch: whatever the route skips.

**Disagreement rule.** If any metric differs by more than 25% between methods or between the agents, we find out why before we believe either. On 15 Oct, 3D→2D read 10.5 s once and 0.17 s once.

### 5.2 What each pass records
- Frames: every rAF gap during play → p50, p95, p99, max, and counts over 33 / 50 / 100 ms.
- Long tasks over 50 ms. In Chrome, LoAF with `scripts[]` attribution.
- Event-loop heartbeat lateness (works in Safari).
- React commits a second (the DevTools hook in `perf2d/measure.mjs`).
- 3D: `window.__frame3d` (draws, triangles, shadow draws, skinned draws, post passes, JS ms, pixel ratio, governor rung).
- Shaders built after the loading cover (`scripts/perf3d/newprog.mjs`), GL contexts alive, `renderer.info.memory`.
- Bytes by type and cache hits. First-load JS sum from `.next/app-build-manifest.json`.
- JS heap (Chrome) at the start, after 10 route loops, and at minute 15.
- Pictures: the same still before and after, phone size. Mean pixel change ≤ 1/255 (the bar used in lag pass 4).
